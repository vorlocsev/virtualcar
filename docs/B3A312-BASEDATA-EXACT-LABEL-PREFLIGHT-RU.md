# B3A312 — проверка точных обозначений XC90 / 2009 / B8444S

Дата: 2026-11-19. Только приватные офлайн-копии. Новый необязательный этап до восстановления 43 профилей.

## Зачем

Владелец выполнил реальный шестисвязный FK-аудит и подтвердил 10/10 синтетических тестов. Для BaseData.VehicleProfile (139578 строк) отсутствующих и неоднозначных целевых ссылок среди шести проверяемых связей нет; есть NULL для обобщённых профилей (модель 51, год 49, двигатель 49848). CarCom T161_Profile (147647 строк) также имеет только однозначные непустые ссылки; NULL по трём измерениям: 52, 53, 51527. Это ещё не выборка XC90 V8 MY2009 и не соответствие двух баз.

Следующая задача — установить, присутствуют ли в **оригинальных справочниках BaseData** точные описания модели XC90, года 2009, двигателя B8444S и можно ли однозначно выбрать их локальные ключи. Код использует только буквальное равенство без регистрозависимости и пробелов по краям. Он не подбирает синонимы, не выдаёт оригинальные ID, названия, VIN и не угадывает значение CID по публичной VIDA 2014D.

## Что делает инструмент

emulator/tools/audit_vida_basedata_exact_labels.py открывает только BaseData.sqlite в режиме mode=ro&immutable=1 и PRAGMA query_only=ON. Используются только подтверждённые таблицы BaseData.VehicleModel, ModelYear, Engine, VehicleProfile и проверенный каталог экспортёра. Инспектор проверяет ровно три именованных описания через параметризованные SELECT. Для каждого измерения выводится категория zero / one / multiple_or_invalid. Если все три имеют ровно одно совпадение, вычисляет **только количества** BaseData.VehicleProfile для точных трёх измерений, модели+года с NULL двигателем и всех двигателей при модели+годе.

При отсутствии совпадений counts=null. Это не доказательство отсутствия XC90/V8: исходные описания могут отличаться от точных обозначений. Даже положительный результат не создаёт p0-exact-43-private.txt и не устанавливает соответствие BaseData.VehicleProfile.Id ↔ CarCom.T161_Profile.identifier.

## Запуск владельцем

На Windows в текущем checkout ветки PR #376 последовательно:

    git pull --ff-only
    py -3 -m unittest discover -s emulator/tests -p test_vida_basedata_exact_labels.py -v
    py -3 .\emulator\tools\audit_vida_basedata_exact_labels.py --folder 'E:\VirtualCar\VIDA-private'

Выполнять третью команду только после успешного прогона 10 тестов и проверки актуального кода. Вывод — ограниченный JSON из чисел, фиксированных булевых и имён категорий. Выходные файлы не создаются, изменения в оригинальной VIDA/SQL/CarCom отсутствуют.

## Границы

Поскольку этап выполняет SELECT по реальным строкам справочников BaseData, он выставляет source_rows_read=true. Но значения описаний и ключей остаются только в памяти процесса. В отчёте всегда false: cross_database_profile_mapping_verified, original_selection_of_43_reconstructed, actual_vida_vehicle_profile_selection_verified, original_readvin_accepted. В отличие от предыдущего этапа inventory, это **ограниченный профильный запрос** к офлайн-экспорту, не прямое чтение SQL Server.

В случае zero или multiple нужно отдельно согласовать и проверить источник более точного критерия, не подгонять отбор под число 43. Никаких J2534, CEM ответа, ReadVin или релиза.
