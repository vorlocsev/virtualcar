# VIDA: сопоставление оригинальных значений FK без обезличивания

Инструмент `emulator/tools/vida_original_fk_value_audit.py` выполняет
**локальное сопоставление значений ключей** между оригинальными JSON-выгрузками
таблиц SQL Server, используя фактический граф внешних ключей, полученный
из `vida_original_schema_reader.py`.

## Источники

Потребуются три или более локальных файла, созданных в предыдущих этапах:

- JSON исходной схемы выбранной базы, полученный
  `vida_original_schema_reader.py`.
- JSON исходной таблицы, содержащей FK, полученный
  `vida_original_table_reader.py` без обезличивания.
- JSON целевой таблицы, содержащей уникальный индекс, на который
  ссылается FK, также полученный `vida_original_table_reader.py`.

Новый инструмент не открывает SQL Server и не посылает команды VIDA.
Он проверяет идентичность базы, имена/порядок столбцов и полноту
выгрузок относительно их собственных метаданных. Для каждого
**действительно объявленного в схеме FK**, обе стороны которого
предоставлены в качестве исходных таблиц, строится сопоставление
*точных представлений значений, возвращённых драйвером*.

Имена FK и колонок, оригинальные строковые значения, ключи и Unicode
**сохраняются без обезличивания**. Совпавшие пары содержат значения
ключей и индексы строк в исходных локальных JSON. Несовпавшие значения
также остаются доступными полностью. Для составных FK используется
порядок колонок из определения SQL Server.

Отдельно учитываются строки источника с `NULL` в одной из FK-колонок.
Такие строки не считаются отсутствующими соответствиями. Повторяющийся
целевой ключ при точном сравнении рассматривается как ошибка.

## Запуск в Windows VMware

Пример с **условными** таблицами, имена которых следует сначала
подтвердить в своей оригинальной схеме:

~~~powershell
$root = Join-Path $env:USERPROFILE 'VIDA-original-private'
$schema = Join-Path $root 'CarCom-original-schema-001.json'
$source = Join-Path $root 'CarCom-T136_InitHw_Profile-original-001.json'
$target = Join-Path $root 'CarCom-T161_Profile-original-001.json'
$out = Join-Path $root 'CarCom-original-fk-values-001.json'

py -3 emulator/tools/vida_original_fk_value_audit.py --schema-report "$schema" --table-report "$source" --table-report "$target" --output "$out"
if ($LASTEXITCODE -ne 0) { throw 'Не удалось сопоставить оригинальные FK-значения' }
~~~

Можно повторить `--table-report` для 2–12 различных таблиц одной базы.
Для DiceTiming применяется тот же инструмент с отдельным
`DiceTiming-original-schema-001.json` и реальными названиями таблиц
этой базы. Смешение таблиц из разных баз в один запуск запрещено.
Связи между CarCom и DiceTiming, реализованные кодом приложения без
обычного SQL FK, **здесь не подтверждаются**.

Объём одного исходного JSON ограничен 50 МиБ, количество строк в каждой
табличной выгрузке не более 5000, итоговый файл не более 50 МиБ.
Результат создаётся исключительно локально новым файлом вне Git.
Файлы с реальными именами/значениями нельзя автоматически включать
в GitHub PR, Actions, CI или опубликованные релизы.

## Принципиальная граница доказательств

Сравнение учитывает **точные типизированные значения из JSON**, но не
реализует SQL Server collation: строки, различающиеся регистром, могут
считаться разными в Python при эквивалентности по правилам SQL Server.
Возможны различия преобразования типов самим ODBC. Два исходных файла
также могут быть получены в разное время, а SHA-256 файлов не является
доказательством их происхождения.

Поэтому даже при полном совпадении всех локальных ключей значения
`database_row_join_verified`, `transactional_snapshot_verified`,
`same_installation_provenance_verified`, `d2_baud_verified`,
`getscript_readvin_runtime_verified` и `client_vin_accepted`
всегда остаются **false**. Для окончательного доказательства реальной
связи необходимо провести разрешённый read-only SQL JOIN внутри самой
оригинальной базы и связать результат с выбором профиля VIDA.
