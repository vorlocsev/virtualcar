# Публичные записи обнаружения Volvo P2

Проверено 01–02.11.2026. Связано с Issue #4. Исследование исходных публикаций;
ответы эмулятора и приватные профили не изменялись.

## Результат

Найдены авторский отчёт об успешном обнаружении S80 MY2002 через VIDA/SardineCAN
и отдельные опубликованные фрагменты DiCE B9F0/B9FB. Полного публичного read-only
сеанса P2 с подтверждённым автомобилем, настройками каналов, временной шкалой от
подключения до обнаружения ECU и результатом клиента в проверенных источниках
не установлено. Причина предупреждения SectorV об обычном режиме остаётся гипотезой.
Совместимость найденных ответов с XC90 V8 MY2009 не подтверждена.

## Наиболее содержательные фрагменты обмена

### S80 MY2002: сравнительный эталон VIDA

По публикации Olaf установлен маршрут diagnostic TX 0x000FFFFE → CEM target 40,
RX 0x00800003 на LS. B9F0 использовался при опросе узлов. Автор приводит список
ответивших LS ECU; HS-узлы через его одноканальное подключение недоступны.
Также показано периодическое чтение A6/1A04 (положение ключа) и A6/1A02
(предполагаемое напряжение). Описана периодическая передача D8; её необходимость
автор обозначает предположением.

Логическая схема наблюдений: подключение VIDA → опрос B9F0 → список LS ECU →
чтение параметров. Это порядок из рассказа автора, **не восстановленная временная
шкала одного capture**. Положение A3 и B9FB в discovery не установлено.
Материал не доказывает ACK обычного режима SectorV. Условия зажигания из
эксперимента с активацией не перенесены в read-only эталон.

### DiCE B9FB: ограниченная временная шкала

Индексированный фрагмент vtl содержит:

| Относительное время | Наблюдение | Следующий шаг клиента |
|---|---|---|
| 0 ms | TX 0x000FFFFE, target 50, B9FB | Не опубликован |
| +62 ms | Первые RX на 0x01200003, начало F9/FB multipart | Не опубликован |
| +62…203 ms | Всего 13 RX, последняя запись через 203 ms после TX | Принятие ответа и переход клиента неизвестны |

Контрольная последовательность младших sequence bits фрагмента циклически
продолжается через wrap; присутствуют start/end flags. Это полезный пример
транспортной структуры, но без исходного файла/канала и контекста он не допускается
как совместимая MY2009 fixture. B9F0 из отдельного сообщения имеет другой RX ID;
эти два фрагмента не объединяются в один сеанс.

## Восемь проверок и сравнение с SectorV

| Проверка | Установлено | Недостающее доказательство |
|---|---|---|
| 1. Происхождение | S80 MY2002 назван автором; C30 исключены; V70 year discrepancy отмечено | Полное описание автомобиля/ECU для DiCE snippets |
| 2. Маршрут | S80 LS125/29-bit и CEM40; B9FB snippet target50/RX0x01200003 | Канал, flags, protocol, baud и фильтры DiCE-сеанса |
| 3. Начало discovery | Авторский успешный результат VIDA и B9F0 опрос | Непрерывная запись подключения и последовательность всех TX/RX |
| 4. A3 | В авторских справочниках операция названа Security Access Mode | Точное назначение конкретного параметризованного запроса SectorV. Положительный A3 ответ для read-only discovery не подтверждён |
| 5. A6 | Показаны чтения CEM1A04/1A02 на S80; в отдельном MY2005 run PR #30 наблюдены CD/50/A6 1A04 и D0D1, оба без RX | Их роль в gate SectorV и данные соответствующего CEM; назначение D0D1 не установлено |
| 6. B9 | Есть отдельные B9F0 и 13-frame B9FB фрагменты | Один полный совместимый сеанс, без смешения источников |
| 7. Другие ECU/P3 | S80 автор сообщает обнаруженные LS ECU | Full scan capture; наличие/отсутствие P3 probes по выдержкам не выводится |
| 8. SectorV | Отдельный MY2005 run [PR #30](https://github.com/vorlocsev/virtualcar/pull/30): 46 requests/8 внутренних connection sessions, invalid=0, route conflicts=0; B9FB40 no_fixture=5, B9FB50 delivered=3; A3/A6 CEM unimplemented/no-RX; normal-mode warning, reachable=0 | Сопоставимый успешный SectorV сеанс или точное условие клиента, вызывающее предупреждение |

В старом post-PR25 backend A6 не маркировался: CD envelope пропускался
классификатором. Это исправлено в PR #30 и проверено отдельным MY2005 run;
два A6 имеют RX=0. Поэтому старое отсутствие метки не доказывало отсутствие
запроса. B9F0 target40/50 в локальном профиле
не имеет fixture; один target50 запрос отдельно отклонён по шине. P3 F114 на
ISO15765 получил CEM/unimplemented/no RX. Три доставки B9FB не доказывают
завершение подготовки CEM.

**Первая временная точка расхождения с успешным клиентом не установлена**:
публичный материал содержит выдержки, а не сопоставимый непрерывный scan.
Проверяемые гипотезы: клиент ждёт отсутствующий ответ на конкретный A3 или B9F0;
либо другую проверку состояния/маршрута. A6 — кандидат для изучения по S80,
не доказанная причина текущего отказа. Нельзя назначать этим гипотезам положительные
ответы из другого поколения.

## Проверка файлов и ограничения анализатора

`analyze_can_csv.py` применён без объявленных baud к пяти CSV. Скорость не извлекается
из timestamp/Bus и не угадывается. Подсчёт request IDs выполнен отдельно по CSV ID;
payload в результаты не сохранён.

| Файл (имя в manifest) | Строк | Принято | Ошибки | 0x000FFFFE / 0x726 / 0x18DA50F1 |
|---|---:|---:|---|---:|
| s60_ignition | 19052 | 19052 | 0 | 0 |
| v70_ignition | 33819 | 33819 | 0 | 0 |
| gauge_ignition (P1) | 98273 | 98273 | 0 | 0 |
| gauge_startup (P1) | 76182 | 71954 | 4228 out_of_order_timestamp | 0 |
| gauge_test (P1) | 344 | 344 | 0 | 0 |

Вывод ограничен выбранными файлами и ID. Деревья репозиториев просмотрены шире;
все CSV коллекций не заявляются проанализированными.

Первоначальный дефект `_request()` — пропуск A3/A6 с D2 length/target
префиксом — исправлен в [PR #29](https://github.com/vorlocsev/virtualcar/pull/29),
HEAD `44edbef4c5bb704e3911aa1327beb8604d0771a0`, восемь групп регрессий и CI
успешны. В прежнем тексте reproducer содержал лишний padding byte: корректный
classic-CAN запрос имеет 8 data bytes, например
`000FFFFE CD40A61A04010000`, а не 9. Усечённые и oversized запросы намеренно
не принимаются исправленным анализатором.

Остаётся другой, конкретно воспроизводимый пробел: RX A6/E6 не поддерживается
этим аудитором. Для проверки взяты **только** отдельные request/reply строки
из авторской статьи S80 MY2002 и обёрнуты в понимаемые анализатором маркеры:

```text
TX (app request) 00 0F FF FE CD 40 A6 1A 04 01 00 00
PassThruReadMsgs -> delivered 00 80 00 03 CD 40 E6 1A 04 1E 00 00
```

Это нормализованная выдержка, не оригинальный непрерывный J2534 файл и не
новая fixture. На HEAD PR #29 запрос распознаётся, но результат:
`rx_frames=0`, `off_route_rx=1`, `unverified/end_of_log`, parse_errors=0;
channel/protocol/baud/window остаются неизвестными. Поэтому такой отчёт не
может доказать отсутствие опубликованного E6 — RX validator знает пока только
другие формы ответа. Дополнение offline аудита A6 можно рассматривать отдельно:
совпадение ID/target/identifier/длины, без объявления ECU identity или normal-mode
success. E3/Security Access в read-only эталон не включается.

## Что нужно для доказательства причины

Нужен read-only capture от подключения до успешного full scan: модель/год/двигатель,
версия CEM и клиента, адаптер, положение ключа, J2534 connect/filter/config,
направление и timestamps всех кадров, channel/protocol/baud/flags, RX counts,
сбросы очередей и результат UI. Желательны успешный и неуспешный SectorV сеансы
с одинаковыми условиями. Вырезать VIN для публикации следует после локального
побайтного анализа, сохранив связь кадров и длины.

Prefixed request recognition и DLL metadata исправлены в отдельных PR #29/#30;
в новом MY2005 run предупреждение воспроизведено без route conflicts.
Для ближайшего исследования нужны успешный сеанс CEM с A6/1A04 и последующим
переходом клиента либо открытое описание именно условия SectorV. Новые источники
не дали такого доказательства; ответ эмулятора по ним добавлять нельзя. Пробел
offline A6/E6 аудита документирован отдельно и не объясняет отсутствие RX в
самом VMware run. Main, Dvinholm и опубликованный prerelease не затрагиваются.
