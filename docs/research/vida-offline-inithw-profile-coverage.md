# P0: приватный профильный аудит прямых связей InitHw (43 XC90 V8 MY2009)

## Основание

В [Issue #4](https://github.com/vorlocsev/virtualcar/issues/4) уже получены
сводки с копий VIDA в VMware:
- 9/9 SQLite и манифестов прошли SHA256/integrity, 269 таблиц;
- шесть основных и шесть InitHw связей CarCom сопоставлены в SQLite без
  пропущенных/неоднозначных целевых записей по опубликованным агрегатам;
- 43 точных профиля XC90 V8 MY2009 в отдельной локальной проверке не имели
  прямых записей T136; один более общий профиль XC90 MY2009 имеет запись T136,
  а связанный InitHw содержит семь заполненных значений;
- BaseData отчёт о двух сохранённых соответствиях профилям не доказывает
  работающий VIDA runtime selection или порядок наследования.

В опубликованной исследовательской реализации VIDA 2014D
[spnda/volvo_vida_db carcom.py](https://github.com/spnda/volvo_vida_db/blob/e2f8ee165e373360d7f7fd0e80298f68c25bc07e/scripts/carcom.py)
`get_hw_settings()` объединяет значения от профилей и применяет
`folderLevel` как приоритет. Это **не доказательство**, что оригинальный
2015A `GetInitHwSettings` выбрал тот же общий профиль для указанного
автомобиля. Отсутствие прямой связи T136 означает только отсутствие
прямой связи, **не отсутствие аппаратных настроек по наследованию**.

## Что делает новый анализатор

`emulator/tools/audit_vida_inithw_profile_coverage.py` принимает **два
приватных файла** UTF-8 с одним точным
`CarCom.T161_Profile.identifier` на строку:

- `--exact-profiles`: ровно **43** независимо отобранных кандидата
  XC90 V8 MY2009, без лишних строк;
- `--general-profiles`: от **1 до 8** отдельно отобранных более
  общих профилей. Это **набор для сравнения, а не доказанные предки**.

Файлы остаются вне Git checkout, в приватном каталоге владельца. Их
состав должен исходить из ранее проверенного локального отбора
модель/год/двигатель, не из догадки или публичного скрипта. Скрипт
**не создаёт и не вычисляет** эти входные списки и не утверждает их
происхождение. Не публикуйте их в Issue, CI или чате.

Анализатор открывает только локальную копию `CarCom.sqlite` через
`mode=ro&immutable=1` + `PRAGMA query_only=ON`, переиспользует
проверку служебного каталога и физических таблиц из
`audit_vida_carcom_inithw_aggregate.py` и делает только
параметризованные `SELECT` по `T161_Profile`,
`T136_InitHw_Profile`, `T131_InitValue`,
`T132_InitValueType`. Не создаёт таблицы, не пишет в SQLite, не
выполняет оригинальный SQL Server и не запускает VIDA.

Отчёт содержит для каждого из двух наборов только числовые классы:
количество переданных/найденных/отсутствующих/неоднозначных
профилей; наличие 0, 1 или нескольких прямых InitHw ссылок;
число уникальных Init-записей и заполненных InitValue; количество
строк типов, в названиях которых *лексически* встречается
`baud` или `speed`. Последнее не является скоростью D2.

Не выдаются приватные ID, названия профилей/параметров,
инициализационные значения, VIN, скорости, CAN ID, SQL, XML, ZIP,
файлы источника или пути. Все неизвестные поля и записи остаются
в локальном процессе; не допускаются неполные/дублированные
входные списки и повторное создание существующего выходного файла.
При ошибке в терминале выводится только название класса исключения.

## Выполнение только владельцем внутри VMware

После code review и **успешного exact-head Windows CI**, создайте два
локальных `.txt` файла **на основе уже подтверждённого частного
каталожного отбора**:

`E:\VirtualCar\VIDA-private\p0-exact-43-private.txt` и
`E:\VirtualCar\VIDA-private\p0-general-private.txt`.

Только когда оба существуют, запустите из проверенного checkout
`development`:

```powershell
$py=(Get-Content 'E:\VirtualCar\Tools\python312.path' -Raw).Trim()
& $py '.\emulator\tools\audit_vida_inithw_profile_coverage.py' --folder 'E:\VirtualCar\VIDA-private' --exact-profiles 'E:\VirtualCar\VIDA-private\p0-exact-43-private.txt' --general-profiles 'E:\VirtualCar\VIDA-private\p0-general-private.txt' --output 'E:\VirtualCar\VIDA-private\p0-inithw-profile-coverage-004.redacted.json'
```

Исходные файлы и локальный отчёт не добавлять в Git. Проверить JSON на
приватные данные перед публикацией агрегированных категорий. Для
повторной проверки нужен другой выходной файл; режим перезаписи
отсутствует.

## Пределы доказательств

Даже 43/43 уникально найденных профиля с 0 прямых InitHw и 1/1
общим с 7 значениями означают только **статическое наличие
кандидатов**, а не фактическую цепочку наследования. Ни
`folderLevel`, ни совпадение с BaseData не доказывают, что VIDA
применила именно этот порядок. Значения baud/speed не раскрываются
и не интерпретируются как настройки выбранного D2 CEM.

Сценарий первоначального `ReadVin` может выбираться на пустом
`VehicleProfile`, а затем идёт отдельный VIN resolver и
ECU Identification. Эта схема остаётся отдельно от InitHw.

Независимо от результатов отчёта:
`original_profile_inheritance_priority_verified=false`,
`d2_baudrate_verified=false`,
`client_vin_accepted=false`, `replay_approved=false`,
`B9FBFrameCount=0`. Никаких J2534/ECU/CEM изменений, SecurityAccess,
программирования, GUI VIDA, releases или переноса в `main`.

## Проверка кода

```powershell
python -m unittest discover -s emulator/tests -p test_vida_inithw_profile_coverage.py -v
python -m compileall -q emulator/tools/audit_vida_inithw_profile_coverage.py emulator/tests/test_vida_inithw_profile_coverage.py
```

12 синтетических тестов исследуют два набора, нулевые прямые
ссылки, неоднозначности, пропущенные профили, пересечения наборов,
дубли, отсутствие раскрытия значений, повторные Init-ссылки,
безопасные SQL-параметры, эксклюзивную запись отчёта и сверку
исходного экспортного каталога.
