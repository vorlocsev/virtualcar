# Virtual Car: VMware, 10 ГБ SQLite и приватный GitHub Runner

Статус: подготовка, **без публикации бинарников и без подтверждённых испытаний на 10 ГБ**.

## 1. Размещение в VMware (Windows 11 x64)

Начальные ориентиры (зависят от ресурсов хоста): 4 vCPU, 8–16 ГБ RAM,
системный SSD C: около 100 ГБ и отдельный виртуальный SSD D: 80–100 ГБ.
Выделение динамического VMDK не заменяет свободное место физического диска.

Пример локального размещения (папки создаёт администратор вручную):

```text
C:\actions-runner\                 # runner и временный checkout
D:\VirtualCar\Lab\catalog\lab.db  # локальный метакаталог SQLite
D:\VirtualCar\Lab\private\        # зашифрованные приватные sidecar-файлы
D:\VirtualCar\Lab\traces\         # локальные лабораторные трассы
D:\VirtualCar\Lab\temp\           # контролируемые временные файлы
```

Не хранить действующую базу в `_work`, в Git-репозитории,
в каталоге установки приложения и в GitHub Actions artifacts.
В реальном приложении путь остаётся явным локальным параметром
(пока предложен также `%LOCALAPPDATA%\VirtualCar\Lab\lab.db`).

**Изоляция:** учётная запись Runner без административных прав,
не имеет доступа к `D:\VirtualCar\Lab\private` и реальной базе.
Работающий J2534 LAB и Runner по возможности разнести по разным VMware VM.
Не запускать чужие PR и fork-код на домашнем Runner.

## 2. Размер, надёжность и границы подтверждения

Ограничения размера в Python, Go и C# подняты с 64 МиБ до **12 ГиБ**:
целевой каталог 10 ГБ плюс запас. Это только guard при открытии файла,
а не доказательство производительности и не лимит общей папки с трассами.
`-wal`, `-shm`, sidecar, `VACUUM INTO` и резервные копии требуют
**дополнительного** места.

Используются WAL, foreign_keys=ON и одиночный контролируемый writer;
данные CAN/J2534 не должны читать SQLite на горячем пути.
Для WAL храните активный каталог на локальном диске VM, не в SMB/NFS-папке.

**Текущие ограничения производительности:** реализации вызывают
`PRAGMA quick_check` при открытии/проверках, поэтому на 10 ГБ
эта операция может заметно замедлить запуск. Требуется отдельный этап:
измерение времени проверки, индексный анализ (`EXPLAIN QUERY PLAN`),
постраничная выборка и осторожная политика checkpoint.
Не отключать проверки целостности без альтернативы.

**Резервное копирование:** Go использует `VACUUM INTO`, C# SQLite Backup API.
Не копируйте единственный `lab.db` обычным способом при активном WAL.
Копия SQLite не включает отдельные зашифрованные приватные файлы; их
резервирование и проверка восстановления нужны отдельно.
Snapshots VMware полезны для отката тестовой ОС, но не заменяют
проверенные резервные копии на другом носителе.

## 3. Регистрируем Windows Runner

1. В приватном репозитории открыть:
   `Settings → Actions → Runners → New self-hosted runner → Windows x64`.
2. Внутри VMware установить **GitHub Runner из команд текущей страницы GitHub**
   в `C:\actions-runner`. Одноразовый токен не публиковать и не отправлять в чат.
3. Выбрать имя `VirtualCar-CI-WIN` и дополнительную метку
   **`virtualcar-win`**. При регистрации выбрать запуск как Windows service.
4. Установить Git, Python 3, Go (под версию `go.mod`), .NET SDK 10,
   а для будущих native gates CMake, VS Build Tools и MSVC x86/x64.
5. Убедиться, что Runner показывает статус `Idle`; на Windows проверить
   `Get-Service "actions.runner.*"`.

Тестовый workflow `.github/workflows/vmware-smoke.yml` запускается
**только вручную**: `Actions → Virtual Car VMware self-hosted smoke → Run workflow`.
GitHub показывает `workflow_dispatch` в интерфейсе только после появления
файла workflow в **default branch**. Пока изменение живёт в PR в `development`,
этот пункт может отсутствовать; не меняйте `main` ради срочного теста.

Workflow запускает только синтетические SQLite-проверки на временных
каталогах, не обращается к `D:`, не пакует исполняемые файлы и **не делает
релизы**. Его `runs-on` требует `[self-hosted, Windows, X64, virtualcar-win]`.
Действующие Linux/Windows workflow остаются без изменений до проверки Runner.

## 4. Запланированные измерения на реальном каталоге

После настройки VM провести локально, без GitHub uploads:

- Небольшая функциональная база, затем 1 ГБ, 5 ГБ и 10 ГБ.
- Время открытия, `quick_check`, выборки и поиска с индексом.
- Импорт, параллельное чтение, сериализованные записи, рост WAL.
- Создание резервной копии и **фактическое восстановление** на пустом диске.
- Сбой во время записи, отсутствие места и повторное открытие без потери данных.

Текущие тесты проверяют только **арифметику лимита 10 ГиБ без выделения 10 ГБ**,
а не производительность базы на 10 ГБ.

## 5. Данные и доступ через чат

В GitHub размещаем только исходники, документацию, обезличенные тесты и
результаты синтетического CI. Реальные VIN, PIN, дампы, диагностические
трассы и локальные токены не попадают в Git, Actions logs или artifacts.
Разработка через ChatGPT идёт через приватные ветки и PR; сам Runner получает
работу от GitHub по исходящему HTTPS.
