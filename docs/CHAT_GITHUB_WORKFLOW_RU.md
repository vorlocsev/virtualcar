# Virtual Car: оптимизированная разработка через чат и GitHub

Статус: процесс работы с приватным репозиторием vorlocsev/virtualcar. Источник кода: GitHub; чат управляет задачами, анализирует и сообщает результаты.

**Продолжение из нового чата:** открыть [NEXT_CHAT.md](../NEXT_CHAT.md) в ветке `development`, сверить зафиксированные там факты с актуальными PR, Issues и CI. В документе есть готовый текст для нового чата.

## 1. Источники истины
- GitHub: исходники, история, Issues, PR, Actions и артефакты лабораторных сборок.
- main: проверенная база. development: интеграция до ручной проверки.
- Рабочий код оригинального виртуального J2534 эмулятора находится в emulator/ ветки development и основан на предоставленных исходниках v0.3.6.6.
- proxy/ и cmd/oneclick/: отдельные средства диагностики, не заменяют эмулятор.
- Предыдущие ZIP dev23-dev30: архивные снимки, не редактировать вместо GitHub.

## 2. Как выполнять очередную задачу
1. Прочитать актуальные Issues, открытые PR и результаты CI; установить точный HEAD SHA.
2. Выбрать один ближайший разблокированный результат. Приоритет: реальные J2534/CEM блокеры и регрессии, затем вспомогательные CAN-исследования.
3. Создать feature/fix ветку от development; не писать непосредственно в main.
4. Подготовить небольшое связанное изменение кода, тестов и, при необходимости, документации.
5. Выполнить 6–8 содержательных проверок для этапа, не умножать тесты без диагностической ценности.
6. Открыть один PR в development, выполнить доступные локальные проверки и ревью diff. Не запускать код непроверенного PR на постоянном VMware-runner.
7. После проверки объединить задачный PR в development: каждый push автоматически запускает VMware CI. Найти запуск по точному SHA итогового коммита, дождаться окончательного статуса и проверить шаги/логи. Если CI упал, исправить причину в отдельном PR и повторить цикл автозапуска. development → main только после успешного CI и согласования.
8. После слияния PR обновить актуальные данные и следующий Issue в `NEXT_CHAT.md`, когда изменились факты контрольной точки; не переписывать всю историю.
9. В чате дать краткую сводку со ссылкой на PR, тестами и одним следующим шагом.

## 3. Работа в чате
- «далее»: автоматически продолжить приоритетную незавершённую задачу, без повторного обсуждения согласованных решений.
- «статус»: прочитать GitHub и назвать HEAD, PR, CI, проблемы.
- «проверить CI»: анализировать только фактические GitHub Actions runs и их вывод.
- «собери для VMware»: использовать CI-артефакт или подготовить один lab-пакет; не выпускать релиз.
- «релиз»: проверка условий + явное подтверждение перед публикацией.
- Отчёт обычно 4 коротких строки: изменение / коммит-PR / проверки / блокер и следующее действие.

## 4. Обязательный автоматический CI на VMware
- Единственный основной проверочный workflow: `.github/workflows/vmware-development-validation.yml` на Windows self-hosted VMware-runner.
- **Каждый push в development автоматически запускает полный CI**, без фильтра по изменённым путям. Обычно запуск создаётся при слиянии проверенного PR; пользователь не должен вручную вызывать `gh`.
- Работа на постоянном runner разрешена только для проверенных owner-push в development. `pull_request` и `pull_request_target` не запускают непроверенные ветки. Ручной `workflow_dispatch` из main сохраняет проверку владельца и allowlist исходников.
- После слияния агент получает точный development HEAD SHA, находит связанный Actions run, проверяет финальный `success` или `failure` и читает логи. Pending/in_progress, отсутствие запуска или успех более раннего SHA не считается успешной проверкой.
- Ошибка CI: выявить корневую причину, подготовить отдельный исправляющий PR, после слияния проверить новый автоматический run. Не требовать от пользователя команд PowerShell или `gh` в штатном процессе.
- Обязательные направления: полный Python-набор, нативные root proxy/RxStatus/J2534-тесты и компиляция x86, legacy emulator x86 DLL/маршруты, Go, C++ x86/x64, .NET и доступные IPC-сценарии. Различать подтверждённые шаги и ещё не выполненные испытания физического J2534 или принятия VIN клиентом.
- Workflow не публикует релизы, установщики или приватные диагностические данные. Merge в main и публикацию релиза не делать автоматически только по зелёному CI.

## 5. Критерии приёмки
- Текущий исходник собирается из чистого checkout, без локальных бинарников и приватных файлов.
- C regression, Python fixture tests, Go tests/vet, PE32/14 J2534 exports выполняются по затронутому проекту.
- B9FB 13 кадров и READ128 не ломаются при изменениях в J2534.
- Нет выдуманных ответов CEM A3/B9F0/A6, нет непроверенных параметров MY2009.
- Приватный VIN и дампы не попадают в GitHub/CI/logs.
- Ручные VMware/SectorV/VDASH тесты отмечаются отдельно, подтверждаются только предоставленными логами.
- При интеграции с действующей DLL нужен отдельный идентификатор/регистрация адаптера, чтобы не заменить рабочую установку.
- Merge в main и публикация release выполняются только после подтверждённых критериев готовности.
