# B3A316 — пассивная проверка кандидата ответа Hardware Session

Задача Issue #4: улучшить доказательства обмена после B9FB без создания
неподтверждённого ответа CEM. Это диагностическая функция виртуального
J2534, **не Security Access и не разрешение на программирование ECU**.

## Факты о клиенте

Из пользовательского статического IL-разбора SectorV:

- `ClientP2HardwareProtocol.Read` (`0x060012FD`) вызывает обработчики
  запросов `A3 02`, `B9 E0`, `B9 F0` в указанном порядке.
- `ClientP2HardwareJ2534Probe.ReadRoute` (`0x060012FA`) после отправки
  запрашивает `ClientP2DiagnosticReceive.Collect` (предел 5000 мс
  в конкретной реализации клиента).
- `ClientP2DiagnosticResponse.Accept` (`0x060012F5`) сверяет адрес,
  сервис `request_service+0x40` и подкоманду, различает отрицательный
  ответ и последовательности D2.
- Для исходящего `A3 02` заголовок положительного ответа имеет
  кандидатные поля `E3 02`. Это **только предполагаемый ответный
  заголовок**. Реальный ответ XC90 V8 MY2009 неизвестен.

В источнике про P1/V50 также описывается общее `A3→E3`, но переносить
его положительные кадры на XC90 V8 MY2009 нельзя. Старые ответные CAN
ID (`0x01200003` для `0x50`, `0x00800003` для `0x40`) являются
транспортными гипотезами из более ранних трасс, а не OEM-подтверждением
маршрутов MY2009.

## Изменения

Функция `p2_hw_inspect_e3_rx_candidate` в `p2_cem_router.c`
проверяет только кандидатный заголовок D2 на канале уже замеченного A3.
В `p2_j2534_bridge.c` проверка изолирована по J2534 CAN-каналу.
`PassThruReadMsgs` вызывает её только для **фактически выдаваемого
клиенту RX**, не при постановке кадра в очередь.

Возможные неизменяемые метки:

- `P2_HW_RX_ORPHAN_E3_CANDIDATE`
- `P2_HW_RX_INVALID_FRAME_CANDIDATE`
- `P2_HW_RX_ROUTE_MISMATCH_CANDIDATE`
- `P2_HW_RX_SUBCOMMAND_MISMATCH_CANDIDATE`
- `P2_HW_RX_WRONG_BUS_CANDIDATE`
- `P2_HW_RX_OTHER_ID_CANDIDATE`
- `P2_HW_RX_LEGACY_ID_CANDIDATE_UNVERIFIED`

Метки не содержат VIN, PIN, ECU-ключ, аппаратный номер, CAN-payload,
обратный ответ или имя автомобиля. Метка `LEGACY_ID_CANDIDATE_UNVERIFIED`
**не равна** статусу `received` у SectorV и **не является** успешной
авторизацией/идентификацией CEM.

Существующий приватный анализатор
`emulator/tools/audit_b3a314_sectorv_hardware.py` дополнен
`native_rx_candidate_counts`. Он никогда не меняет
`positive_hardware_session_verified=false`.

## Проверки

`python3 -m unittest discover -s emulator/tests -p 'test_b3a316_hw_rx.py' -v`

23 синтетические группы в двух C-файлах: заголовок, маршрут,
подкоманда, битрейт, CAN ID, длина, отсутствующий A3, очистка
при переподключении, два независимых канала, ISO15765, 11-bit CAN,
старый B9FB, отсутствие изменения состояния и безопасные метки.

Два дополнительных Python теста для B3A314 требуют, чтобы кандидат
RX оставался unverified даже при клиентском `no-reply`.

Тесты на синтетических кадрах не подтверждают подлинность ответов
реального XC90, клиентскую приёмку Hardware или оригинальную VIDA.
На уровне эмулятора положительные ответы CEM **не создаются**.
Никакие изменения физического CEM, DiCE/реестра или внешних приложений
не выполняются.

## Последующий gate

Для реального Hardware Session PASS нужны: разрешённый и проверенный
источник ответа конкретного CEM; подтверждение точной физической
сети/ID/профиля MY2009; статус приёма ответа именно в SectorV,
а затем успешная обработка E0 и F0. До этих данных оставить
`HardwareSession=NOT_VERIFIED`.
