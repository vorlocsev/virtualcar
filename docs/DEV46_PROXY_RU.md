# dev46: пассивная диагностика ISO15765 в J2534-прокси

Прокси по-прежнему передаёт все 14 функций исходной DLL с исходными аргументами
и возвращает её результат. Новые события наблюдают доставку через J2534, а не
внутреннюю работу ECU. Положительные диагностические ответы не создаются.

## Журнал

Используются существующие `VCAR_TRACE_REAL_DLL` (абсолютный путь к исходной DLL)
и `VCAR_TRACE_LOG_PATH`. Без второго параметра журнал остаётся в
`%TEMP%\VirtualCarJ2534Trace.jsonl`. Для разных процессов задавайте разные журналы:
идентификаторы каналов и последовательностей локальны процессу.
Сборка `bash build_dev26.sh` сохраняет прежние имена файлов; dev46 обозначает
новую схему диагностики, а не выпуск или установку новой оригинальной DLL.

В том же JSONL сохраняются прежние записи **schema 15** и новые **schema 46**.
Существующие отчёты OneClick продолжают читать schema 15; подробности dev46
находятся в JSONL. При анализе schema 46 отбирайте её явно. В ней CAN ID — числа,
в прежней схеме они остаются шестнадцатеричными строками.

Новые события:

| Событие | Смысл |
| --- | --- |
| `filter_start`, `filter_stop`, `filters_clear` | Результат операции, ID/тип и число отслеженных активных фильтров |
| `iso15765_tx` | Один принятый TX, класс сервиса и наличие соответствующего FLOW_CONTROL_FILTER |
| `iso15765_rx` | Один доставленный RX, отдельная классификация индикаций и отрицательных ответов |
| `iso15765_wait_end` | Наблюдение завершено без сопоставленного финального RX; причина и прошедшее время |
| `rx_clear`, `observer_capacity` | Очистка границы наблюдения или превышение ёмкости |

Каждая запись содержит канал, поколение подключения, протокол и скорость.
`filter_start` также показывает `rx_pattern_id`, `rx_mask_id`, `flow_control_id`,
`filter_usable` и размер заголовка. Сохраняются только CAN ID/маска ID, типы,
флаги, размеры, время и статические категории. Payload, VIN, DID/PID,
extended-address byte, пути и строки приложения в журнал не записываются.
Параметры запросов, необходимые для сравнения DID/PID, остаются только в памяти.

## Сопоставление TX/RX

1. Успешное подключение создаёт поколение канала с его протоколом и скоростью.
2. Фильтры учитываются только после успешного изменения. Неуспешные stop/clear
   сохраняют состояние. PASS/BLOCK тоже входят в число активных фильтров.
3. Для ISO15765 (ProtocolID 6) TX может получить `sequence`, если его адрес
   соответствует ровно одному отслеживаемому FLOW_CONTROL_FILTER.
4. RX проверяется по тому же каналу, RX mask/pattern, 11/29-bit формату,
   extended-address маске, сервису и, где применимо, DID/PID/подфункции.
5. Единственный кандидат в пределах **5000 мс** получает
   `relation=filter_time_service_candidate`, `sequence` и `elapsed_ms`.
   Несколько запросов/фильтров дают неоднозначность; последний TX не выбирается.

Поддерживаются категории OBD чтения, UDS чтения данных/DTC/памяти,
KWP чтения идентификации и TesterPresent. Остальные сервисы получают
`other_service` без сопоставления. `START_OF_MESSAGE` и TX-индикации не завершают
ожидание. NRC `0x78` оставляет запрос открытым в том же временном окне;
финальный отрицательный ответ завершает его. Заголовок `62 DID` без значения
остаётся неполным свидетельством.

`ms` — время наблюдения после возврата вызова DLL, `device_timestamp_us` —
отдельные часы адаптера. Они не вычитаются друг из друга. Разность host ms
учитывает переполнение 32-битного счётчика. Это время доставки/наблюдения,
а не время реакции ECU или настроенный тайм-аут клиента.

Принятые префиксы учитываются при WriteMsgs `STATUS_NOERROR`/`ERR_TIMEOUT`;
доставленные — при ReadMsgs `STATUS_NOERROR`/`ERR_TIMEOUT`/`ERR_BUFFER_OVERFLOW`.
Количество должно помещаться в исходно запрошенный буфер и быть не больше 128.
Другие ошибки не разрешают чтение буфера; исходные коды и количества остаются
в schema 15. `status` в schema 46 значим для операций фильтров; TX/RX — уже
отобранные наблюдения, их исходный статус смотрите в schema 15.

## Границы доказательств

- Сопоставление — кандидат по доступным метаданным. Оно не доказывает принятие
  VIN клиентом или причину отсутствия ответа внутри оригинальной DLL.
- `filter_stopped_no_final_rx` означает интервал до снятия фильтра, а не
  доказанный ECU timeout. Истечение окна проверяется при следующем TX/RX;
  фонового таймера и дополнительных J2534 вызовов нет.
- Заголовки фильтров размером 4/5 байт пригодны для сопоставления. Фильтры с
  масками payload учитываются, но остаются непригодными для сопоставления.
  Функциональные адреса не преобразуются в предполагаемые физические адреса.
- До 64 каналов, 128 фильтров и 128 ожидающих запросов на процесс. При потере
  состояния `incomplete=1` запрещает уникальное сопоставление до успешной очистки
  фильтров или нового подключения. Живые записи не перезаписываются.
- Disconnect, успешный Close соответствующего устройства, повторное подключение,
  CLEAR_MSG_FILTERS и CLEAR_RX_BUFFER завершают соответствующие ожидания.
- Вызовы реальной DLL выполняются без блокировки наблюдателя. При параллельных
  Write/Read RX может быть замечен до регистрации принятого TX и остаться без пары.
  Порядок наблюдений не доказывает внутренний порядок обработки ECU.
- Ручные VMware/SectorV/VDASH и физический J2534 этим изменением не проверены.

## Проверки

`build_dev26.sh` выполняет прежние регрессии моста/классификатора и Go,
добавляя на GCC и Clang восемь групп тестов наблюдателя, восемь групп тестов
реальных функций прокси с подставной DLL и проверку JSON/отсутствия payload.
Среди проверок — частичные результаты, ошибки, READ128/13 RX B9FB,
отрицательные ответы, неоднозначность, ёмкость, 11/29-bit и extended addressing.
CI также проверяет Windows PE32, отсутствие CRT и 14 PassThru экспортов.
Оригинальная DLL, её B9FB replay и `emulator/` не изменяются.
