# B3A317 — время и происхождение кандидата E3 при Hardware Session

Цель: улучшить достоверность пассивного наблюдения CEM после A3/02,
не генерируя положительного ECU-ответа и не выполняя Security Access.

## Проверенная основа

Исходный наблюдатель B3A316 классифицировал E3/02 при совпадении
адреса, потенциального CAN ID и ранее видимого TX A3 на том же
J2534 CAN-канале. Однако **временной связи не было**. Повторный кадр,
доставленный значительно позже, мог получить ошибочно сильную
диагностическую метку.

Локальные результаты SectorV для предшествующей лабораторной
сессии: ответ B9FB из донорской фикстуры — 13/13 через J2534;
на Hardware 0x50 и 0x40 — no-reply около пяти секунд. Это не
является доказательством подлинной идентичности XC90 V8 MY2009.
Пять секунд в B3A317 — **окно наблюдения по клиентскому тесту**,
а не доказанный аппаратный тайминг всех CEM Volvo.

## Реализация

- `p2_bridge_inspect_tx_at` сохраняет монотонную метку времени
  отправленного A3/02 только в текущем J2534 CAN-канале.
- Обычные TX, периодические TX, неверный/непринятый TX, повторное
  подключение или смена скорости сбрасывают прежний временной маркер.
- `p2_bridge_inspect_hw_rx_at` запускается исключительно в точке
  **выдачи через PassThruReadMsgs**, использует тот же монотонный
  таймер и допускает диагностическую категорию «в пределах окна»
  только при 0 <= RX - TX <= 5 000 000 микросекунд.
- Если RX пришёл до TX, после окна или не имеет timestamped A3,
  записываются отдельные безопасные статусы. Второй совпавший
  кадр внутри того же окна маркируется как дубль.
- `START_OF_MESSAGE` без реального raw CAN payload игнорируется.
- Публичные и исходные данные о ключе, VIN, номере CEM, ревизии
  или транспортных байтах в новый отчёт не выводятся.

**Всё равно не подтверждается:** положительный ECU-ответ,
успешная сессия A3, аутентичность источника CAN RX, корректность
старых ответных CAN ID для XC90 V8 MY2009 и декодирование
аппаратного номера. Результат `TIMED_LEGACY_ID_CANDIDATE_UNVERIFIED`
по определению не означает успешную авторизацию.

Новое окно не имитирует handshake. Эмулятор по-прежнему не
отправляет ответ E3 и не изменяет существующие очереди, фильтры
или воспроизведение B9FB. Legacy API для статического анализа
оставлен без изменений; исполняемый J2534 путь использует
строгую timed-проверку.

## Проверки

`python -m unittest discover -s emulator/tests -p 'test_b3a317_hw_timing.py' -v`

17 синтетических C-групп: orphan RX, канальная метка TX,
изоляция каналов, RX до TX, совпадение в окне, дубль,
точно 5 секунд, 5 секунд + 1 мкс, инвалидирование после B9FB
и постороннего TX, отсутствие timestamp в старом API,
START_OF_MESSAGE, смена скорости, disconnect/reconnect,
невалидный TX, отсутствие изменения ECU состояния и метки.

В `test_b3a314_sectorv_hardware.py` добавлены ещё две
проверки приватного анализатора: никакая timed-метка,
дубль или просрочка не повышают
`positive_hardware_session_verified` до true.

## Следующая приёмка

После успешного CI необходим разрешённый проверенный образец
ответа для целевого CEM и его реально наблюдённая доставка
в тот же клиентский сеанс. Только после фактического
`SectorV hardware-session result=received` и подтверждённого
разбора E0/F0 можно пересмотреть статус Hardware.
