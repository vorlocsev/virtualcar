# dev31: безопасный анализ обнаружения CEM по J2534 (Issue #4)

Инструмент `emulator/tools/audit_j2534_discovery.py` анализирует только чтение и **не формирует ответы ECU**, INI/реплеи, ключи, Security Access или запись конфигурации.

## Использование на локальной машине

```powershell
python emulator/tools/audit_j2534_discovery.py "C:\path\private-j2534.log" --output "C:\path\cem-audit.json"
```

- Исходный диагностический лог остаётся только локально. **Не публикуйте его, даже если часть VIN уже замаскирована.**
- Новый JSON содержит перечисленные категории запросов, CAN ID, channel, protocol, baud, формат 11/29 bit, счётчики RX и статус. В нём **нет** payload, VIN, PID, имени процесса или исходного пути.
- Поддержаны строки оригинального `PassThruWriteMsgs()/ReadMsgs()` и VirtualCar `TX (app request)` / `PassThruReadMsgs -> delivered`. Промежуточные `RX (simulated)` не считаются доставкой клиенту.
- Новое журналирование `TX/RX/CLEAR_RX context ... (BE)` добавляет ChannelID, ProtocolID, флаги, baud и временную метку в микросекундах. Событие `PassThruDisconnect channel (BE)` позволяет завершать только нужный канал. Старые логи не содержат этого контекста: тогда соответствующие поля `null`/`unknown`, **а не угаданный канал**.
- Отчёт `window_ms` означает время между TX и последним доставленным RX, если имеются согласованные отметки. Это не время обработки ECU, не доказательство парсинга VIN и не показатель успешного обнаружения CEM.
- `delivered` означает лишь поступление RX через J2534, не принятие диагностической программой. `no_fixture`, `unsupported`, `timeout`, `partial_rx`, `unverified` не превращаются в «успех».
- D2 B9F0/FB/FC проверяются только по видимым заголовкам, счётчику и признаку финального кадра. Реальность VIN, корректность checksum и идентичность MY2009 **не утверждаются**.
- P3 идентификация по 0x726/0x18DA50F1 только диагностируется; существование валидного положительного ответа **не доказано**.
- Источник не перезаписывается. JSON создаётся только если новый путь ещё не существует.

## 8 групп офлайн-регрессий

1. Полный 13-кадровый B9FB, канал, скорость и временное окно.
2. Некорректная D2 последовательность и отсутствующий финальный кадр.
3. Отсутствие фикстуры, отклонение strict route, реальный J2534 timeout.
4. Два канала, 11/29-bit и P3 маршруты.
5. Смешанные RX CAN ID и недостоверное склеивание.
6. `CLEAR_RX_BUFFER` и повторная генерация, без смешения старого и нового ответа.
7. Старый формат DiCE J2534-лога, временные отметки и неизвестные метаданные.
8. Сокрытие личных идентификаторов и запрет трактовать доставку как подтверждение ECU.

CI проверяет эти тесты вместе с C-тестом READ128/B9FB, Go tests, Windows x86 cross-build и экспортами J2534. **Windows/VMware/физический J2534 этим не подтверждаются.**

Следующее действие после CI: исследовать обезличенный полный лог реального запуска и отделить `no_fixture` от ошибок маршрута/времени. Приватный INI, VIN и дампы в GitHub не добавлять.

## dev32: проверка P3 ISO-TP без подмены идентификации

Анализатор теперь отдельно обрабатывает одиночные CAN ISO-TP кадры, First Frame + Consecutive Frame, последовательность CF, длину ответа, а также готовые UDS сообщения `ISO15765` J2534. Промежуточные CAN Flow Control (`30 xx xx`) не сбрасывают ожидающий запрос. Первый кадр без продолжения остаётся `partial_rx`, а некорректный порядок и длина имеют причину `invalid_iso_tp_framing`.

Ответ `7F 22 NRC` классифицируется как `negative_response`, несоответствующий DID как `unverified`, а корректно доставленный транспорт как `delivered`. Даже `62 F1 14` при полном транспорте **не подтверждает** VIN, принадлежность ECU или успех клиента. Анализируются лишь 3 начальных UDS-байта и счётчики длины/кадров; VIN и содержимое ответа в отчёт не включаются.

Восемь синтетических групп `test_audit_p3_transport.py` проверяют: (1) стандартный и расширенный маршрут, (2) готовую выдачу ISO15765, (3) FF/CF и неполный ответ, (4) Flow Control, (5) ошибки ISO-TP, (6) отрицательные ответы, (7) неверный DID и CAN ID, (8) многоканальность, очистку RX и приватность. Все проверки только offline; отсутствие реального подтверждённого MY2009 CEM и VMware-клиента остаётся блокером.

## dev33: незавершённый UDS ResponsePending и проверка длины DID

При чтении P3 идентификации ответ `7F 22 78` является **промежуточным** (`responsePending`), а не окончательным отказом ECU. В отчёте он даёт `unverified / uds_response_pending_only`; последующий `62 F1xx <data>` завершает наблюдение как `delivered` (только транспорт), а финальный `7F 22 NRC`, отличный от `78`, классифицируется `negative_response`. При явно записанном `PassThruReadMsgs timeout` после ожидания результат `timeout / j2534_timeout_after_response_pending`.

У сообщения `62 F1xx` должны существовать данные после трёхбайтного заголовка. Один только заголовок `62 F1 14` не подтверждает даже законченный DID-ответ и получает `partial_rx / missing_uds_identifier_data`. **Содержимое и подлинность VIN по-прежнему не проверяются**. Добавлен только числовой счётчик `response_pending_frames`, без сохранения полезной нагрузки, приватных идентификаторов или полного NRC-потока.

Восемь синтетических групп: (1) одиночный NRC78, (2) ожидание→положительный ответ, (3) несколько ожиданий→окончательный отказ, (4) ожидание→J2534 timeout, (5) аналогичный цикл через ISO15765, (6) неполный заголовок без DID-данных, (7) минимальный транспортный ответ с DID-данными, (8) два параллельных канала, неверный DID и отсутствие персональных сведений в JSON. Существующие B9FB/READ128 и dev31–32 regression tests должны сохраняться.

Проверки в VMware и на реальном J2534 не выполнялись; текущий лабораторный результат **не означает идентификацию XC90 MY2009**.


## Полные D2 A3/A6 envelopes в DLL (Issue #4)

Классификатор backend и `process_d2` раньше принимали только CA/CB/CF:
полный CD/CC/CE запрос не получал известный маршрут CEM. Теперь общая
проверка принимает CA–CF, target 40/50, service A3/A6, не более восьми
байтов и не меньше объявленной префиксом длины (prefix − C8 + 1).
Паддинг допускается. Усечённые и oversized запросы не маркируются как CEM.
Это проверка формы запроса, не подтверждение смысла параметров или ECU.

Результат остаётся `unimplemented_probe/no_response`: E3/E6 не создаются,
Security Access не реализуется. B9-классификация и replay не изменены.
Связанные исследования: PR #28; текстовый анализатор: PR #29.

Восемь групп synthetic host-регрессий для обоих targets и services:
точная длина всех CA–CF; padded CAN; усечение; oversized CAN; неправильный
prefix; чужой target; другой service; чужой CAN ID. В каждой проверяется
классификатор, один terminal event и отсутствие RX/response_generated.
Дополнительно идентичные байты на ISO15765 не считаются D2 CAN.
Существующий suite проверяет B9FB/READ128 и остальные маршруты.

Локально: старый development не проходит новый shape assertion; исправленный
MSVC x86 host suite проходит. Python: 116 tests, 1 expected skip (host C
integration в этой Python-среде); C suite запущен отдельно. CI проверяется
на точном HEAD PR. Новая DLL в SectorV/VMware пока не испытывалась.

Дополнительное локальное наблюдение: в последнем процессе накопленного
текстового лога есть два CD/50/A6 TX, CAN channel 1, 500000 bit/s.
Граница процесса не доказана как граница одного сканирования, поэтому это
не связывается автоматически с 46-request MY2005 backend suffix. Параметры,
PID и raw log не публикуются. Пропуск CD доказан кодом и регрессией;
причина отказа SectorV normal mode этим не доказана.
