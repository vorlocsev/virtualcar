# B3A30: записи TX VIDA и атрибуция ошибок WriteMsgs

Задача [#320](https://github.com/vorlocsev/virtualcar/issues/320): локальный
read-only аудит **формата и происхождения записей журнала**, а не проверка
работы ECU. Инструмент `tools/audit_vida_b3a30_tx_coverage.py` читает один
существующий текстовый журнал и создаёт новый категориальный JSON.
Исходный файл он не меняет. Оригинальную VIDA, DLL, Registry32, автомобиль
и приватные журналы для разработки и тестов запускать или открывать не нужно.

B3A29 сообщил `NO_SINGLE_COMPLETE_TX_FRAME=18`. Это объединённая категория
неполных, неоднозначных и пакетных записей: она **не означает отсутствие
фактического TX** и не доказывает, что все 18 ошибок относятся к K-Line.
Для этих исходных 18 событий B3A30 остаётся **NOT TESTED** до отдельного
разрешённого запуска владельцем локально. Синтетические тесты не заменяют
этот запуск и не удостоверяют происхождение ECU.

## Что попадает в отчёт

JSON содержит только фиксированные поля, категории и суммарные счётчики:

- параметризованные `PassThruWriteMsgs(ChannelID,PASSTHRU_MSG,NumMsgs,Timeout)`
  и классы размера пакета: одна запись или больше одной;
- маркеры `---> (index)` точного компонента `J2534ChannelMana` отдельно
  от маркеров других компонентов;
- альтернативные записи `PassThruWriteMsgs() msg[n].Data = [...]`;
- категории ошибок `WriteMsgs ERR_NOT_SUPPORTED`, кандидатов Connect
  и буквальной формы полностью записанной одиночной команды.

Нулевой счётчик TX относится только к **поддержанным записям этого журнала**.
Он не является счётчиком действительных вызовов драйвера или передач шины.
В отчёте нет исходных строк, payload, VIN, путей, PID, значений потоков,
времени отдельных событий, идентификаторов скриптов, хешей исходников
или секретов. Не публикуйте исходный журнал для объяснения категории.

`write_calls` и `write_batch_single/multiple` относятся к точному компоненту;
суффиксы `_other_component` и `_unscoped` учитывают другие заголовки и
буквальные совпадения неизвестного формата отдельно, без атрибуции вызова.

| Категория ошибки | Значение |
| --- | --- |
| `NO_TX_RECORD` | Найден подходящий Write-вызов, но нет подходящей записи TX. |
| `TX_RECORD_OTHER_COMPONENT` | В окне есть TX другого компонента; его payload не принимается как TX точного компонента. |
| `MULTI_MESSAGE` | Write объявляет пакет из нескольких сообщений; это не одиночный полный TX. |
| `AMBIGUOUS_OR_MALFORMED_RECORD` | Нарушена форма, последовательность индексов либо однозначность записей. |
| `COMPLETE_SINGLE_LOGGED_TX` | Один Write с одним полным согласованным TX-маркером в поддержанном формате. Это только полнота записи. |
| `UNMATCHED_ERROR` | Нет однозначно подходящего предшествующего Write-вызова. |

Счётчики `error_connect_candidates` независимы от полноты TX:

- `SAME_THREAD_ISO9141_10400_UNACKNOWLEDGED`: свежий кандидат Connect
  того же потока с указанным режимом; успешность Connect не подтверждена;
- `SAME_THREAD_OTHER_UNACKNOWLEDGED`: свежий кандидат того же потока
  с иным указанным режимом; успешность также не подтверждена;
- `CROSS_THREAD_PROTOCOL_UNVERIFIED`: кандидат другого потока;
  его протокол не переносится на Write по одному числовому ChannelID;
- `MISSING_OR_STALE`: подходящего свежего кандидата нет.

Они охватывают только ошибки, сопоставленные с Write-вызовом;
у `UNMATCHED_ERROR` кандидат Connect не назначается.

`complete_literal_shapes` использует только категории
`RELAY_CLOSE_LITERAL`, `B9F0_LITERAL`, `TEARDOWN_LITERAL`, `OTHER_LITERAL`.
Совпадение буквальной формы не подтверждает реальный транспорт, успешный
Connect, поля ABI `PASSTHRU_MSG`, локальный ACK, OEM RX или ReadVin.
В частности, отсутствующие в VIDA.log поля ABI нельзя восстановить по байтам.

## Границы корреляции

Строгие правила заголовка, вызова, маркера и ошибки повторно используются
из `audit_j2534_discovery.py`. Общая таблица каналов `_VidaText` не служит
доказательством успеха Connect и не используется для переноса протокола
между потоками. Потоки связываются только внутри одной logsession.

Для Write → error требуется тот же поток, монотонное время, максимум
20 исходных строк и 5000 мс. Кандидат Connect ограничен 200 исходными
строками и 30000 мс. Отсутствующее, неверное или обратное время нарушает
положительную корреляцию; переход через полночь не восстанавливается
предположением о дате. Это может оставить запись несопоставленной.

Новый вызов в том же потоке прерывает предыдущий. `Starting new logsession`,
Open/Close, Disconnect и повторный Connect с тем же ChannelID разрывают
соответствующее состояние. Числовой ChannelID может использоваться снова.
TX неизвестного потока делает активные Write-кандидаты неоднозначными;
RX неизвестного потока прерывает корреляцию. Неизвестный scope учитывается
в `unvalidated_tx_records`, без утверждения о повреждении самого payload.
Точность атрибуции ограничена тем, что журнал действительно записал;
пропущенный вызов или неизвестный формат нельзя восстановить догадкой.

TX принимается только при строгих целых токенах, допустимой длине и
последовательности индексов. Поддерживается и четырёхбайтная буквальная
форма teardown: минимальная длина CAN-кадра из старого аудитора здесь
не применяется. Дубликаты, пропуски, перемешанные синтаксисы и повреждённые
записи не превращаются в положительный результат.
Без явно записанного ABI DataSize потерю целых байтов в конце payload
невозможно обнаружить по синтаксису. Полная запись здесь означает один
синтаксически целый лог-маркер; полноту исходного PASSTHRU_MSG она не доказывает.

Альтернативный `msg[n].Data` связывается с Write только при точном
заголовке `J2534ChannelMana`, том же потоке и предшествующем
параметризованном вызове. Legacy-строка без поддержанного заголовка
учитывается только в inventory. Синтетическая проверка такого расположения
записей не утверждает, что оно найдено в исходном журнале VIDA.

В `development` нет B3A14 и K-Line whitelist из закреплённого
[Draft PR #319](https://github.com/vorlocsev/virtualcar/pull/319)
(`50040f5d11aa2bdfce202db55fa1a638d4d49a9a`). Они изучены как граница
доказательств; переносить runtime или менять ветку #319 для B3A30 не нужно.
Совпадение одной из трёх форм не проверяет дополнительные opt-in флаги,
timeout и поля ABI того whitelist.

## Синтетические проверки: Python 3.12 / PowerShell 5.1

Из корня checkout новой ветки, без приватных данных:

```powershell
py -3.12 --version
py -3.12 -m unittest discover -s emulator/tests -p test_audit_vida_b3a30_tx_coverage.py -v
py -3.12 -m unittest discover -s emulator/tests -p test_audit_vida_text.py -v
py -3.12 -m unittest discover -s emulator/tests -p test_audit_j2534_discovery.py -v
py -3.12 -m unittest discover -s emulator/tests -p test_audit_vida_script_selection.py -v
```

Для каждого вызова проверяйте `$LASTEXITCODE`: ожидается `0`.
Результаты фактически исполненных проверок фиксируются в новом Draft PR.
Эти команды не собирают и не запускают J2534 DLL и не запускают VMware.

## Следующая команда только для владельца, opt-in

**Не исполняется при разработке или в CI.** Владелец указывает существующий
локальный журнал и новый JSON внутри своего заранее созданного приватного
каталога. Пример использует вымышленные пути; замените их локально:

```powershell
$vidaLogPath = 'C:\OwnerPrivate\VIDA.log'
$ownerOutputPath = 'C:\OwnerPrivate\Reports\B3A30-new.json'
& py -3.12 .\emulator\tools\audit_vida_b3a30_tx_coverage.py `
    --vida-log $vidaLogPath --output $ownerOutputPath
if ($LASTEXITCODE -ne 0) { throw 'B3A30 fail-closed; output not accepted' }
```

Файл результата не должен существовать: создание эксклюзивное,
перезапись запрещена, в том числе при совпадении входного и выходного пути.
Каталог результата должен контролироваться владельцем. Не используйте
каталог синхронизации, artifacts или рабочее дерево Git для приватного запуска.

Вход ограничен 32 МиБ, 200000 строками и 32768 байтами на строку;
декодирование — строгий UTF-8 с допустимым BOM. Последняя строка должна
заканчиваться переводом строки: оборванный хвост отклоняется. Неизвестную
кодировку, oversized-вход или ошибки доступа инструмент отклоняет с кратким
сообщением без исходного содержимого и путей. Исправлять или перекодировать
оригинальный журнал ради положительного результата не нужно.

После owner-local запуска анализируйте только новый категориальный отчёт.
До него причины исходных 18 ошибок, фактический TX, подлинный ECU RX
и автоматическое чтение VIN оригинальной VIDA остаются непроверенными.
