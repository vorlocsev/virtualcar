# B3A54: приватный VIN и уже существующий B9FB lab-профиль

## Почему этот этап нужен

В более раннем приватном B3A12 был проверен VIN, заданный владельцем
в лабораторном `virtualcar.ini` и закрытом профиле автомобиля; значения
согласованы, персональные данные не публиковались. Отдельно ранее
подготавливался приватный **13-кадровый** кандидат Volvo P2 D2 `B9FB`.

Это **не** тот же факт, что оригинальная VIDA успешно считала VIN.
Исторические B3A50/B3A52/B3A53 установили: оригинальный клиент завершил
`READ VEHICLE` с ошибкой, в замороженной сессии было шесть запросов
`B9FB` и ноль доставленных RX; оба базовых `0x40/0x50` загружали
ноль кадров. В текущем активном `virtualcar.ini` они тоже объявлены
с `FrameCount=0`. Сравнения старого INI по полному хешу не было.

## Реализованная проверка

`emulator/tools/audit_vida_b3a54_private_b9fb_vin.py` принимает:
- **явно выбранный** локальный приватный `*.ini` с
  `[Vehicle] VIN` и кандидатом `[D2_50] B9FBFrame*`;
- необязательный **текущий** активный `virtualcar.ini` для
  сравнения двух файлов по полному набору кадров и response-ID
  **только в памяти**;
- необязательный приватный `vehicle-identity.json` из B3A12 со
  структурой `Vehicle.VIN` и `Vehicle.ModelYear`. Значения
  сравниваются исключительно в памяти, а JSON не публикуется.

Сначала используются имеющиеся native-подобные ограничения
FrameCount/ResponseId/восьмибайтовых кадров, затем уже существующий
`audit_p2_b9fb_shape.audit_frames` и
`import_p2_trace.validate_response`. Лишь для **одного
документированного 13-кадрового примера с 88-байтным телом**
проверяется буквальное совпадение семнадцати байтов по смещению
11 с приватным VIN из секции Vehicle. Отдельное шестизначное поле
сравнивается с суффиксом VIN как наблюдаемое равенство байтов,
**не как подтверждённое поле номера шасси**.

Статусы `equal`, `different`, `not_assessable` означают только
локальную согласованность. Случай опубликованного донорского примера
с заменённым VIN явно маркируется `not_oem_my2009`. Самостоятельное
заявление приватного INI о происхождении *не* удостоверяет его.
`replay_approved=false` и
`oem_my2009_origin_verified=false` сохраняются при любых входах.

**Ни исходный VIN, ни 13-кадровый ответ, ни ResponseId, ни путь,
ни PID, ни хеш приватного профиля никогда не выводятся.** Файлы
читаются без записи; ограничения размера 512 KiB, запрет симлинков,
отказ от неоднозначных секций и от одинаковых входных путей.

## Запуск только на своей Windows/VMware

В доверенном checkout `development` (не загружая профиль в GitHub):

```powershell
py -3 .\emulator\tools\audit_vida_b3a54_private_b9fb_vin.py --private-profile "C:\PRIVATE-P2\my-lab-profile.ini" --active-ini "C:\VirtualCarVMware\virtualcar.ini" --identity-json "$env:USERPROFILE\Downloads\VirtualCar-VIN-MY2009-Apply\vehicle-identity.json"
```

Пути обоих INI условные и требуют локальной подстановки.
Путь к JSON соответствует ранее использованной папке
`VirtualCar-VIN-MY2009-Apply` в Downloads; исходный JSON
должен существовать на этой машине. Если активный файл отсутствует, допускается только
`--private-profile`, но сравнительный статус станет
`not_supplied`. Скрипт не запускает VIDA и не включает воспроизведение.

Не путать с публичным `emulator/virtualcar-p2-b9fb-lab-vin.ini`:
это пример **на основе публичного донора с подставленным
синтетическим VIN**. Его формат не удостоверяет XC90 V8 MY2009.

## Корреляция с существующим приватным JSON

При указании `--identity-json` программа проверяет только
`Vehicle.VIN` и категорию `Vehicle.ModelYear`. Она сравнивает
VIN из JSON с `[Vehicle] VIN` кандидата и, если структура B9FB
является известным 88-байтным примером, с наблюдаемым
17-байтным полем. Категории
`identity_json_vs_private_ini_vin` и
`b9fb_field_vs_identity_json_vin` равны `equal`,
`different` или `not_assessable`; значения VIN не выводятся.
`declares_my2009` означает лишь заявление конфигурации.
Дубликаты JSON-ключей отклоняются.

## Следующий gate

Результат владельца должен содержать только категории:
`private_b9fb_declared_count`, `d2_transport`,
`published_88_byte_shape`, `vin_field_vs_private_vin`,
`observed_six_digit_field_vs_vin_suffix`,
`active_candidate_exact_frame_match`, `profile_provenance`.
При наличии расхождений нужно проверить сам приватный профиль
**локально**. Если всё согласовано, это по-прежнему
только **синтетическая лабораторная фикстура**, а не проверенный
OEM-профиль. Для следующего оригинального VIDA-сеанса отдельно
нужны достоверная CAN/response-ID маршрутизация, аутентификация
загруженной DLL, фактический ECU RX и принятие VIN в GUI.

PR должен пройти восемь регрессионных offline-групп, затем
exact-head доверенный VMware CI. `main`, физический J2534,
`StrictRouting`, настоящий `virtualcar.ini`, исходные логи,
VIN и B9FB RX в C DLL не меняются. Issues #326 и #4 остаются OPEN.
