# Virtual Car: StrictJ2534Filters (этап 41)

**Лабораторная опция**, по умолчанию выключена. Режим предназначен для проверки контракта J2534 CAN и ISO15765. Это не гарантия совместимости с конкретной моделью Volvo, VIDA, SectorV или VDASH.

## Включение

В `virtualcar.ini` рядом с используемой DLL:

```ini
[Diagnostics]
StrictJ2534Filters=1
```

Отсутствующее значение и `0` оставляют неизменным прежний `legacy`-путь. Настройка читается при `PassThruOpen`; закройте и откройте устройство после изменения INI.

## Контракт при включённом режиме

- **CAN (ProtocolID=5):** `PASS_FILTER` и `BLOCK_FILTER` разрешены; `FLOW_CONTROL_FILTER` возвращает `ERR_NO_FLOW_CONTROL (23)`. Без подходящего `PASS_FILTER` новые входящие CAN-кадры не выдаются. `BLOCK_FILTER` имеет приоритет над `PASS_FILTER`. Маска и шаблон должны иметь одинаковую длину 4–12 байт: четыре байта CAN ID (big-endian), до восьми байт данных кадра.
- **ISO15765 (ProtocolID=6):** принимается только `FLOW_CONTROL_FILTER`. `PASS_FILTER` и `BLOCK_FILTER` возвращают `ERR_INVALID_FLAGS (6)`. Для `FLOW_CONTROL_FILTER` требуются три указателя `MaskMsg`, `PatternMsg`, `FlowControlMsg`, каждый с `ProtocolID=6` и `DataSize=4` (стандартная CAN ID-адресация). Отсутствие `FlowControlMsg` даёт `ERR_NULL_PARAMETER (4)`; несовместимый протокол `ERR_MSG_PROTOCOL_ID (21)`; некорректная длина `ERR_INVALID_MSG (10)`.
- **Приём ISO15765:** ответ выдаётся только при совпадении маски и шаблона с CAN ID ответа; многокадровый синтетический UDS-ответ остаётся **одним собранным `PASSTHRU_MSG`**. Если настроен `EmitIsoRxStart=1`, START_OF_MESSAGE выдаётся только для разрешённого ответа. После `CLEAR_MSG_FILTERS`, удаления фильтра либо повторного подключения старый фильтр больше не пропускает сообщения.
- `FlowControlMsg` сохраняется в параметрах фильтра и используется как **виртуальный маршрут FC**. Текущая модель ECU уже формирует собранные ISO15765-ответы, поэтому она **не посылает настоящие CAN Flow Control CTS**. Наличие записи `synthetic flow-control route armed` в локальном логе не является записью USB/CAN-трафика DiCE.

## Ограничения

- Расширенная ISO15765-адресация с пятым байтом, конкурирующие ECU с одним RX CAN ID, потоковая отправка CTS с реальным STmin/BS и полноценный аппаратный ISO-TP транспорт **не реализованы в этом этапе**. Эти ситуации не следует считать проверенными.
- Существующие B9F0/B9FB/B9FC/D2 фикстуры, защищённые диагностические сервисы и реальные данные автомобиля не изменяются. Ни VIN донора, ни непроверенные CEM A3/A6 ответы не добавляются.
- Строгая политика включается на всё тестовое устройство при открытии из INI. Изменение конфигурации при активных каналах не поддерживается.

## Проверка

Обычные host C/Go/Python регрессии остаются режимом `legacy`. В GitHub Actions запускается настоящий собранный `VirtualCarJ2534.dll` Windows x86:

1. `verify_native_filter_contract.ps1 -Mode legacy`, контроль обратной совместимости.
2. `verify_native_filter_contract.ps1 -Mode strict`, контроль отказов, жизненного цикла фильтров и синтетического многокадрового VIN на ISO15765.
3. `tests/virtualcar_test.c`, дополнительная host-проверка блокировки RX, ISO15765 Flow Control, CAN payload filter, очистки и повторного подключения.

Все испытания относятся к синтетическому LAB. Проверка реального клиента SectorV/VDASH, гостевой VMware и физического J2534/DiCE требует отдельной evidence-bound процедуры.
