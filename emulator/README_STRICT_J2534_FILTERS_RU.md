# Virtual Car: StrictJ2534Filters (этап 41)

**Лабораторная опция**, по умолчанию выключена. Режим предназначен для проверки контракта J2534 CAN и ISO15765. Это не гарантия совместимости с конкретной моделью Volvo, VIDA, SectorV или VDASH.

## Включение

В `virtualcar.ini` рядом с используемой DLL:

```ini
[Diagnostics]
StrictJ2534Filters=1
```

Отсутствующее значение и `0` оставляют неизменным прежний `legacy`-путь. Настройка читается при `PassThruOpen`; закройте и откройте устройство после изменения INI.

## Контракт при включённом режиме

- **CAN (ProtocolID=5):** `PASS_FILTER` и `BLOCK_FILTER` разрешены; `FLOW_CONTROL_FILTER` возвращает `ERR_NO_FLOW_CONTROL (23)`. Без подходящего `PASS_FILTER` новые входящие CAN-кадры не выдаются. `BLOCK_FILTER` имеет приоритет над `PASS_FILTER`. Маска и шаблон должны иметь одинаковую длину 4–12 байт: четыре байта CAN ID (big-endian), до восьми байт данных кадра.
- **ISO15765 (ProtocolID=6):** принимается только `FLOW_CONTROL_FILTER`. `PASS_FILTER` и `BLOCK_FILTER` возвращают `ERR_INVALID_FLAGS (6)`. Для `FLOW_CONTROL_FILTER` требуются три указателя `MaskMsg`, `PatternMsg`, `FlowControlMsg`, каждый с `ProtocolID=6` и `DataSize=4` (стандартная CAN ID-адресация). Отсутствие `FlowControlMsg` даёт `ERR_NULL_PARAMETER (4)`; несовместимый протокол `ERR_MSG_PROTOCOL_ID (21)`; некорректная длина `ERR_INVALID_MSG (10)`.
- **Приём ISO15765:** ответ выдаётся только при совпадении маски и шаблона с CAN ID ответа; многокадровый синтетический UDS-ответ остаётся **одним собранным `PASSTHRU_MSG`**. Если настроен `EmitIsoRxStart=1`, START_OF_MESSAGE выдаётся только для разрешённого ответа. После `CLEAR_MSG_FILTERS`, удаления фильтра либо повторного подключения старый фильтр больше не пропускает сообщения.
- `FlowControlMsg` сохраняется в параметрах фильтра и используется как **виртуальный маршрут FC**. Текущая модель ECU уже формирует собранные ISO15765-ответы, поэтому она **не посылает настоящие CAN Flow Control CTS**. Наличие записи `synthetic flow-control route armed` в локальном логе не является записью USB/CAN-трафика DiCE.

## Дополнение этапа 42: несколько ECU и конфликтующие фильтры

В строгом режиме (`StrictJ2534Filters=1`) при регистрации нового ISO15765 `FLOW_CONTROL_FILTER` проверяются идентификаторы `PatternMsg` (RX CAN ID) и `FlowControlMsg` (физический CTS/TX CAN ID). Если любой из двух совпадает с любой стороной уже установленного FC-фильтра **на этом канале**, возвращается `ERR_NOT_UNIQUE (24 / 0x18)`; перекрывающиеся маски RX также отклоняются, чтобы не создать два претендующих маршрута. Никакой новый FilterID не выделяется при такой ошибке. В другом канале такая же пара может использоваться независимо.

Для **синтетического многокадрового** ответа помимо совпадения RX CAN ID требуется полная маска `FF FF FF FF` и равенство `FlowControlMsg` физическому адресу запроса конкретного ECU: например, `7E8 → 7E0` или `72E → 726`. Для функционального TX `7DF` ответ каждого ECU сопоставляется **со своим** физическим FC ID, а не с адресом функционального TX. Если FC ID неверен, RX подавляется и фиксируется как отвергнутый фильтром. Широкие маски разрешены для коротких (single-frame) синтетических ответов, но не для многокадровых.

**Граница доказательств:** это программная проверка маршрута готовых UDS-ответов внутри Virtual Car, **не эмуляция аппаратной отправки CTS** и не утверждение о поддержке специфического DiCE CAN/RFQ поведения. Проверка `ERR_NOT_UNIQUE` согласуется с публичной справкой J2534: https://scandoc.org/en/develop/j2534/pt_start_msgfilt.html. Отдельного испытания на физическом DiCE нет.

## Дополнение этапа 43: пятый адресный байт и атомарность очереди

В J2534 **ISO15765_ADDR_TYPE = 0x80** обозначает ISO15765 extended addressing. При этом заголовки `MaskMsg`, `PatternMsg` и `FlowControlMsg` для такого протокола могут содержать **5 байт** (CAN ID + address byte). См. SAE J2534-1:2004, раздел A.2.1, а также https://www.scandoc.org/en/develop/j2534/pt_start_msgfilt.html .

В нынешнем Virtual Car пятый байт адреса **не моделируется в транспортном уровне**. Поэтому в opt-in `StrictJ2534Filters=1`:
- `PassThruStartMsgFilter` с установленным `ISO15765_ADDR_TYPE` в `TxFlags` любого ISO15765 фильтр-сообщения возвращает `ERR_NOT_SUPPORTED (1)`, не создаёт фильтр и не расходует `FilterID`.
- Запрос ISO15765 `PassThruWriteMsgs` с `TxFlags & 0x80` возвращает `ERR_NOT_SUPPORTED (1)` до разбора ECU; `NumMsgs` указывает число сообщений, принятых до ошибки. Ответ ECU не формируется.
- Пятибайтовые заголовки без соответствующего флага адресации по-прежнему отклоняются `ERR_INVALID_MSG (10)`. Заявленной поддержки Toyota/BMW extended addressing **нет**.

Когда `EmitIsoRxStart=1`, многокадровый синтетический ответ создаёт пару сообщений `START_OF_MESSAGE` + собранный `PASSTHRU_MSG`. **В строгом режиме очередь обязана иметь два свободных слота; при 0 или 1 слоте пара отбрасывается целиком**, а лабораторная телеметрия регистрирует `queue_full`. Это исключает «осиротевшую» индикацию либо payload при переполнении. Приём коротких сообщений остаётся без START_OF_MESSAGE.

Восемь C-групп и отдельный `strict_queue` Windows x86 probe проверяют поведение на границах 62/63/64 элементов, восстановление после переполнения и независимость двух каналов. **CI и тесты подтверждают только лабораторную модель**; реакция настоящего DiCE и клиентов SectorV/VDASH не изучена.

## Ограничения

- Расширенная ISO15765-адресация с пятым байтом, конкурирующие ECU с одним RX CAN ID, потоковая отправка CTS с реальным STmin/BS и полноценный аппаратный ISO-TP транспорт **не реализованы в этом этапе**. Эти ситуации не следует считать проверенными.
- Существующие B9F0/B9FB/B9FC/D2 фикстуры, защищённые диагностические сервисы и реальные данные автомобиля не изменяются. Ни VIN донора, ни непроверенные CEM A3/A6 ответы не добавляются.
- Строгая политика включается на всё тестовое устройство при открытии из INI. Изменение конфигурации при активных каналах не поддерживается.

## Проверка

Обычные host C/Go/Python регрессии остаются режимом `legacy`. В GitHub Actions запускается настоящий собранный `VirtualCarJ2534.dll` Windows x86:

1. `verify_native_filter_contract.ps1 -Mode legacy`, контроль обратной совместимости.
2. `verify_native_filter_contract.ps1 -Mode strict`, контроль отказов, жизненного цикла фильтров и синтетического многокадрового VIN на ISO15765.
3. `tests/virtualcar_test.c`, дополнительная host-проверка блокировки RX, ISO15765 Flow Control, CAN payload filter, очистки и повторного подключения.

Все испытания относятся к синтетическому LAB. Проверка реального клиента SectorV/VDASH, гостевой VMware и физического J2534/DiCE требует отдельной evidence-bound процедуры.
