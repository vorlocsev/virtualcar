# Backend JSONL audit: контрольная точка CEM / Issue #4

Утилита `emulator/tools/audit_backend_evidence.py` работает **только с локальным обезличенным JSONL потоком** Virtual Car `virtualcar-backend-v1`. Исходные J2534-логи и приватный профиль автомобиля не нужны. Анализ не формирует CAN-ответы или фикстуры и ничего не записывает в эмулятор.

Включите только локальную мета-телеметрию в `virtualcar.ini` рядом с J2534 DLL и перезапустите диагностический клиент:

```ini
[Diagnostics]
BackendTelemetryEnabled=1
```

Текущая DLL сохраняет JSONL в `%LOCALAPPDATA%\\VirtualCar\\dev47-backend.jsonl` активного пользователя Windows. Этот файл отличается от старого текстового лога с CAN-пакетами; не путайте их.

Пример запуска (Windows с установленным Python):

```powershell
python emulator\tools\audit_backend_evidence.py "C:\private\backend.jsonl" --output "C:\private\backend-audit.json"
``` 

Результат содержит только порядковые номера сессий и запросов, категорию маршрута, ChannelID, протокол и скорость, число поставленных в RX/выданных/потерянных сообщений, длительность от TX до терминального события, а также статус и краткую фиксированную причину. Личные идентификаторы, значения запросов, VIN, payload, имена процессов, PID, исходные `session_id`/`request_id`, пути и любые неизвестные поля **не копируются**. Выходной файл создаётся только если отсутствует; источник не изменяется.

Статусы:
- `delivered`: J2534 выдал хотя бы один RX и backend выпустил терминальное `responded` без свидетельства потери. **Не доказаны** полноценность транспорта, декодирование VIN или принятие автомобиля диагностическим клиентом.
- `no_fixture`: явное `missing_profile`.
- `unsupported`: явное `unsupported_bus` или `unhandled_request`.
- `partial_rx`: RX был выдан, а затем ответ прерван или потерян.
- `timeout`: только при явном терминальном `read_timeout` (текущий backend DLL **не генерирует** этот тип события). Обычное отсутствие RX/закрытие канала не объявляется таймаутом.
- `unverified`: нет достоверного терминального события, произошёл сброс до получения RX, нарушена последовательность событий или не хватает данных.

**Границы применимости:** backend JSONL намеренно не содержит CAN ID, 11/29-bit признака, сервиса и DID. Поэтому анализатор оставляет `can_id=null`, `service=null`, `id_format=unknown` и не утверждает, что запрос был именно A3, A6, B9F0 или B9FB. Для такой атрибуции используется существующий локальный `audit_j2534_discovery.py` с исходным J2534-логом. Его результат нужно сопоставлять в защищённой лабораторной среде, не подменяя отсутствующую корреляцию по уникальному ID.

Проверки: 8 групп `emulator/tests/test_audit_backend_evidence.py` (доставка, отсутствие фикстуры, аборт, сессии и каналы, противоречивые терминалы, приватность, недопустимость выдуманного timeout, неизменность файлов). Это offline-проверки; VMware/SectorV/VDASH и физический J2534 не проверяются CI. Новых CEM-positive ответов, Security Access и записи ECU нет.

## Точное определение запроса в JSONL (Issue #4)

При следующей сборке DLL появляется событие `probe_classified` с полем `probe` из **закрытого списка**. Определяются D2 CEM 40/50: A3, A6, B9F0, B9FB и B9FC; P3 CEM 0x726 и 0x18DA50F1: F114, F1B0, F1A3, F106, F190. Метка создаётся при получении TX, до формирования ответа. CAN FC не формирует новую метку. В токен не включаются реальные байты VIN, параметры конфигурации, произвольные CAN ID и содержимое ответа.

Анализатор принимает только известные токены и по ним выдаёт `service`, `target`, `can_id` и `id_format`. Если метка отсутствует (старый JSONL или неизвестная команда), эти поля остаются `null` / `unknown`. Разные метки одного запроса дают `unverified`, а не ложное подтверждение. Метка доказывает только форму диагностического TX, **не** идентичность автомобиля, корректность B9FB, OEM-поддержку службы или прочтение VIN. Эта телеметрия остаётся опциональной и не меняет J2534 ответы.

## Проверка целостности журнала

Аудитор не считает доставку доказанной, если отсутствует предшествующее `rx_queued` для `rx_dequeued`, повторяется `tx_received`, нарушен порядок событий или локальная монотонность часов, либо при терминальном `responded` остались невыданные поставленные в очередь кадры. Такие записи получают `unverified`. Событие `rx_dropped` не считается извлечением из очереди: оно также возникает при неудачной попытке постановки кадра. Терминальное `no_response` с RX-событиями тоже противоречиво. Это проверка качества мета-журнала, а не подтверждение полной диагностики CEM.
