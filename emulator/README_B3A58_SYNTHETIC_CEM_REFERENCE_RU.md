# B3A58: синтетический B9FB как эталон виртуального CEM

## Решение владельца

Физического CEM нет. Для Virtual Car **каноническим рабочим ответом
виртуального CEM** назначается существующий 13-кадровый Volvo P2 D2 B9FB
с эталонной формой из B3A6/B3A7. Искать независимый OEM-захват для
разрешения лабораторного воспроизведения больше не требуется.

Это соглашение **об устройстве эмулятора**, а не заявление о происхождении
с заводского ECU. Фактическая приёмка оригинальной VIDA ReadVin и
идентификации ECU остаётся отдельным тестом.

## Реализация

`emulator/tools/build_synthetic_cem_b9fb_profile.py` берёт только
хранящийся в репозитории **публичный синтетический** образец
`emulator/virtualcar-p2-b9fb-lab-vin.ini` и *локальный приватный*
`vehicle-identity.json` владельца. Разрешены схемы VIN/ModelYear,
которые уже распознаёт B3A55.

Перед генерацией проверяются: MY2009, VIN 17 ASCII, присутствие
13 валидных восьмибайтовых D2 кадров, 0x50/F9/FB, 88-байтовая
форма, соответствие VIN в шаблоне и в кадрах, однозначная загрузка
FrameCount и отсутствие неподтверждённых активных B9F0/B9FC.

**Меняются только 17 байт VIN-поля** внутри B9FB и локальные поля
`[Vehicle] VIN/ModelYear`, а также безопасные метки синтетического
происхождения в `[P2]`. Другие байты ответа, в том числе
шестизначное поле, не корректируются и не истолковываются как
заводской идентификатор. `[D2_40]` остаётся отключённым,
`[D2_50]` содержит 13 кадров. Роутинг/ResponseId не переизобретаются.

Новый профиль создаётся через exclusive-create. **Существующий
`virtualcar.ini` не перезаписывается.** VIN, байты D2, приватные
пути, содержимое JSON не печатаются и не отправляются в GitHub.

## Локальное создание в VMware владельца

Из доверенного checkout `development`:

```powershell
$identity = "$env:USERPROFILE\Downloads\VirtualCar-VIN-MY2009-Apply\vehicle-identity.json"
$privateDir = Join-Path $env:LOCALAPPDATA 'VirtualCar\OwnerPrivate\B3A58'
New-Item -ItemType Directory -Path $privateDir -Force | Out-Null
$output = Join-Path $privateDir 'synthetic-cem-reference.ini'
py -3 .\emulator\tools\build_synthetic_cem_b9fb_profile.py --identity-json $identity --output $output
```

На повторном запуске выберите **новое** имя выходного файла: создание
с тем же именем намеренно отклоняется. Созданный INI содержит личный VIN,
поэтому никогда не публикуйте его и не прикладывайте к Issues.

### Активация

На Windows native `VirtualCarJ2534.dll` читает
**`virtualcar.ini` в каталоге DLL**. Для фактического включения нового
эталона владелец должен в остановленном изолированном тестовом
клиенте проверить текущий INI, сохранить резервную копию и
**явно** установить созданный приватный INI под этим именем.
Это действие не выполняется скриптом; не трогать установку VIDA,
физический адаптер или соседние пользовательские файлы автоматически.

Проверка загруженного профиля: в следующем J2534-сеансе должно
наблюдаться `D2_50/B9FB frame-count=13` и успешная доставка
13 кадров только по совпадающему маршруту 0x50 и параметрам канала.
`D2_40`, B9F0 и B9FC не должны получать вымышленных ответов.

## Границы приёмки

- `CAN/D2/13-frame shape`: проверяется offline синтетическими тестами.
- `Generated private profile`: создан только на машине владельца.
- `Original VIDA ReadVin`: NOT_VERIFIED до реального GUI-сеанса.
- `OEM provenance`: NOT_ASSERTED, не является требованием Virtual Car.
- `Physical J2534`: NOT_TESTED.

Восемь offline-групп охватывают корректность, изменение только
VIN-поля, неверную идентичность/MY, искажённые кадры, лишние
активные ответы, запрет перезаписи, неоднозначный JSON и отсутствие
утечек в CLI.
