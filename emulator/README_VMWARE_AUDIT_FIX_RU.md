# Issue #4: согласованность маршрутов после VMware audit

Основание: обезличенный `virtualcar-backend-audit-v1`, предоставленный
01.11.2026: 38 запросов / 14 сеансов / 0 RX. При продолжении локально найден
исходный backend JSONL и повторно обработан новым аудитором. Пользовательский
отчёт, исходный журнал и частные файлы в репозиторий не входят.
База анализа: development `ad333635d37fffea651733745af5f1ce3f35d2ba`.

## Что доказывает предоставленный отчёт

- 20 B9FB: target 40 / 125 kbit/s и target 50 / 500 kbit/s, по десять,
  `no_fixture/explicit_missing_profile`. В опубликованном synthetic VMware
  профиле намеренно нет активных CEM D2 фикстур. Это ожидаемое отсутствие
  данных, а не основание включать вымышленные кадры. Ещё два B9FB target 50
  на 250 kbit/s отклонены как `unsupported_bus`; маршруты не расширяются.
- Четыре `0x726 / 22 F1 14`, CAN и ISO15765, 500 kbit/s:
  `unsupported/unhandled_request`. VMware профиль имеет только ECM;
  отсутствующий узел P3 CEM не добавляется. Существующий лабораторный F114
  обработчик при явно настроенном узле не является проверенным OEM ответом.
- Шесть `unverified/explicit_no_response` в сеансе 13: маршрут CEM, нет
  allowlisted probe. Сервис неизвестен; это не доказательство A3/A6 либо B9FB.
- Шесть `unverified/inconsistent_route_or_channel` в сеансе 14: первые три
  на канале 1 / 500 kbit/s, последние три на канале 2 / 125 kbit/s.
  Старый отчёт объединяет конфликт route/channel/protocol/baud в одну причину.
  Повторный аудит исходного JSONL сохранил все прежние счётчики, invalid=0,
  и показал для всех шести только `evidence_conflicts=[route]` и
  `observed_routes=[ECM, ECU_OTHER]`. В каждом случае исходная цепочка:
  tx_received/UNKNOWN → route_selected/ECM → request_completed/ECU_OTHER,
  no_response/no_response. Канал, протокол и скорость внутри каждого
  request не меняются. Это подтверждённое противоречие меток телеметрии;
  журнал не даёт основания считать эти шесть случаев смешением каналов.

## Воспроизведённый дефект и исправление

Физический suppressed TesterPresent `3E 80` выбирает ECM/CEM, но прежний
код завершает его с жёстко заданным ECU_OTHER. Два канала воспроизводят
такой конфликт независимо, без смешения данных. Повторный аудит подтвердил
совпадение ошибочной цепочки маршрутов со всеми шестью случаями в журнале.
Сервис этих пользовательских запросов не маркирован: нельзя утверждать,
что это именно TesterPresent, либо восстановить payload из метаданных.
Новые тесты сначала завершились FAIL на исходной реализации, затем PASS
после исправления. Поведение шины при этом остаётся прежним: ноль RX.

Маршрут физического запроса теперь одинаков на выборе и молчаливом
завершении. Дополнительные D2_Node сохраняют ECU_OTHER на missing_profile,
unsupported_bus и response_generated. Functional `0x7DF` получает один
агрегированный ECU_OTHER на транзакцию независимо от числа/порядка узлов;
это не утверждение об ответе отдельного CEM. Данные и логика ответов не меняются.

Аудитор сохраняет прежние status/reason и добавляет поля транзакции:

- `observed_routes`: сортированный список только разрешённых маршрутов;
- `evidence_conflicts`: сортированный список `route`, `channel`, `protocol`,
  `baud`, по которым события одного request расходятся.

Исторические конфликты остаются unverified. Дополнительные поля не
восстанавливаются из старого audit.json: нужен повторный запуск нового
аудитора над приватным исходным backend JSONL, локально в VMware.
Формат v1 сохраняется, изменение полей аддитивное. Поля не содержат payload,
VIN, исходных request/session ID или путей; неизвестные входные поля отброшены.

## Восемь групп проверки

1. Физическое молчаливое завершение ECM/CEM/other, CAN/ISO15765, HS/LS;
   отдельное сохранение unverified/explicit_no_response без догадок о сервисе.
2. D2_Node без фикстуры; старые конфликты маршрута остаются unverified.
3. D2_Node на неверной скорости; конфликт channel/protocol/baud различим.
4. Точный synthetic D2 replay и terminal после dequeue; нарушения lifecycle
   по-прежнему блокируют delivered. Сохранены прежние B9FB 13 кадров/READ128.
5. Functional suppression/protected silence: одна транзакция/один маршрут;
   перемежающиеся каналы в анализаторе не объединяются.
6. Functional fanout коротких ответов без противоречивых маршрутов;
   новые поля выдерживают подстановку частных/неразрешённых значений.
7. B9FB без фикстур/P3 без узла остаются без RX; прежние проверки строгого
   baud, A3/A6 без ответов, ISO-TP, фильтров и очереди сохраняются.
8. Opt-out и реальная цепочка C-emitter → Python-auditor: 18 synthetic
   транзакций, нет конфликтов, сохранены no_fixture/unsupported/unverified;
   delivered не означает принятие ответа клиентом или идентификацию.

В CI путь `VIRTUALCAR_ROUTE_EVIDENCE` связывает C suite с Python-проверкой.
Вне CI для интеграционной проверки задать его перед запуском C harness
и Python suite. Без переменной только эта интеграционная проверка пропускается.
Файл содержит исключительно synthetic события тестового обработчика и не
публикуется в артефактах. Локально подтверждены MSVC x86 host suite и
44 Python-проверки аудитора, включая интеграцию. Остальные проверки сборки,
Python и Go выполняет CI на точном HEAD PR.

## Граница результата и следующий шаг

Новые DLL/клиент в VMware и физический J2534 в этом этапе не испытывались;
обнаружение XC90 V8 MY2009 не подтверждено. Issue #4 остаётся открытым.
Повторный аудит исходного журнала выполнен: старые ошибочные записи
сохраняют unverified и не исправляются задним числом. Следующий шаг —
новый read-only VMware сеанс с CI сборкой этого PR: проверить отсутствие
новых конфликтов меток, не выдавая это за идентификацию CEM. Шесть
explicit_no_response остаются без известного сервиса. Для B9FB требуются
подтверждённые совместимые фикстуры; положительные CEM ответы не создаются
автоматически.

PR направлен только в development. Main, Dvinholm, отдельные draft PR
и опубликованный VMware prerelease/tag/assets не изменяются.
